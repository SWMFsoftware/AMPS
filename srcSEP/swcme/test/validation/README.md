# SWCME observational validation campaign

This directory contains validation against observations and independent model
products. It is intentionally separate from the deterministic C++ regression
suite in `test/core`, `test/1d`, and `test/3d`: a unit or analytical test can
prove an implementation contract, while a validation case measures whether the
implemented physics is useful against evidence not generated by SWCME.

The layout is case-owned and registry-driven. Every implemented case has one
self-contained subdirectory. The global runner discovers cases only through
`campaign.json`, invokes the command declared by the case's `case.json`, and
aggregates results without importing the case's science code.

## Directory structure

```text
test/validation/
├── README.md                  campaign and extension contract
├── campaign.json             ordered VP01-VP16 registry and dependencies
├── run_validation.py         model-independent global comparison runner
├── test_run_validation.py    focused orchestration and exit-code tests
├── output/                    ignored timestamped campaign evidence
├── vp01/                     radial density/Leblanc case
├── vp02/                     Parker angle/polarity case
├── vp03/                     background thermodynamics case
├── vp04/                     CDAW height-time case
├── vp05/                     LineupCAT multipoint DBM case
├── vp06/ … vp16/             shock, geometry, connectivity, coupling cases
└── common_model_driver.cpp   shared warning-clean public-API probe
    ├── README.md              scientific question, method, and thresholds
    ├── case.json              global-runner launch/result contract
    ├── data/
    │   ├── PROVENANCE.json    immutable upstream metadata and checksums
    │   └── raw/               downloaded, ignored upstream archives
    ├── download_data.py       atomic checksummed data acquisition
    ├── reference_solution.py  independent published-equation oracle
    ├── vpNN_model_driver.cpp  production SWCME physics evaluator
    ├── run_vpNN.py            case reduction, comparison, and plots
    ├── test_reference_solution.py
    └── output/                direct-case evidence and figures
```

All sixteen cases now use sibling lowercase directories. Data, reference logic,
case-specific tests, figures, and documentation remain in the case directory.
VP06-VP15 use `common_model_driver.cpp` only as a thin production-API probe;
their independent equations and evidence classification remain case-owned.

## Running validation

Run these commands from `swcme/test`:

```sh
# Inspect registered scope without executing a case.
make validation-list

# Test only the global orchestration contract.
make validation-test

# Execute one case; CASE may also be a comma-separated list.
make validation-case CASE=VP01

# Execute all cases that currently have implementations, using cached inputs.
make validation-implemented

# Evaluate the complete registered VP01-VP16 campaign, using cached inputs.
make validation-campaign
```

`validation-case`, `validation-implemented`, and `validation-campaign` accept
extra runner options through `VALIDATION_ARGS`.

### Run all VP01-VP16 cases without downloading data

Use this mode when every case's required input is already present under its
`data/raw/` directory. The runner verifies the cached files and their pinned
checksums before analysis; it does not contact any remote data service:

```sh
make validation-campaign
```

The equivalent direct Python command is:

```sh
python3 validation/run_validation.py --all
```

This is the preferred command for repeat analyses, offline execution, and CI
jobs that restore a separately populated validation-data cache. A missing or
invalid input is reported by the owning case as a setup error, and dependent
cases are marked `BLOCKED`; the runner never silently replaces missing evidence
with generated model output.

### Run all VP01-VP16 cases and acquire reference data

On a fresh checkout, pass `--download` through `VALIDATION_ARGS` so the global
runner invokes every selected case's `download_data.py` before its analysis:

```sh
make validation-campaign VALIDATION_ARGS="--download"
```

The equivalent direct Python command is:

```sh
python3 validation/run_validation.py --all --download
```

VP01-VP05 acquire or reuse their pinned external observational products and
verify the recorded checksums. VP06-VP16 do not require bulk network data: their
acquisition helpers materialize and verify immutable analytical, literature,
coupling, or held-out benchmark manifests. Existing valid files are reused, so
`--download` is also safe for a reproducible rerun and does not force an
unnecessary transfer.

Both commands execute cases in VP01-to-VP16 priority order, enforce registered
dependencies, generate PNG/EPS figures by default, and create an isolated
timestamped evidence directory beneath `validation/output/`. Add `--no-plots`
when only numeric and machine-readable evidence is required:

```sh
make validation-campaign VALIDATION_ARGS="--download --no-plots"
```

### Individual and implemented-scope examples

The same option forwarding works for one case, a comma-separated subset, or
the currently implemented scope:

```sh
make validation-case CASE=VP01 VALIDATION_ARGS="--download"
make validation-case CASE=VP06,VP07 VALIDATION_ARGS="--download"
make validation-implemented VALIDATION_ARGS="--no-plots --output /tmp/swcme-validation"
```

The direct Python equivalents are:

```sh
python3 validation/run_validation.py --case VP01
python3 validation/run_validation.py --case VP01,VP02 --download
python3 validation/run_validation.py --implemented
python3 validation/run_validation.py --implemented --download
```

`--case` runs the named case even when its registered prerequisites were not
selected, and records those omitted prerequisites in the summary. In a
multi-case or full-campaign run, a later implemented case becomes `BLOCKED` if
one of its selected prerequisites did not pass. Cases always execute in the
registry's priority order rather than command-line order.

## Status and exit-code contract

| Status | Meaning |
| --- | --- |
| `PASS` | Every applicable scientific criterion in the case passed. |
| `FAIL` | A scientific comparison failed, or any selected case failed. |
| `INCOMPLETE` | Evidence is explicitly partial, blocked, or not implemented. |
| `NOT_IMPLEMENTED` | The case is registered but its case package is planned. |
| `BLOCKED` | A selected prerequisite did not pass. |
| `ERROR` | The case contract, process, or returned result was invalid. |
| `NOT_APPLICABLE` | A traceable retired case does not apply. |

The global process returns `0` for PASS, `1` for FAIL, `2` for INCOMPLETE, and
`3` for a registry, selection, or setup error. All VP01-VP16 packages are now
implemented. A campaign PASS remains scoped by each result's `evidence_class`
and `limitations`; in particular, the bundled V6 coupling benchmarks do not
claim external AMPS particle-transport skill.

## Common evidence products

Each global run creates an isolated output directory. Without `--output`, the
name includes UTC time, selection mode, and process ID so concurrent jobs do not
share evidence. The directory contains:

| Product | Contents |
| --- | --- |
| `manifest.json` | Invocation, environment, source hashes, selected cases, and overall result. |
| `summary.json` | Complete machine-readable case records and aggregate status. |
| `summary.csv` | Compact result table for CI and review. |
| `metrics.csv` | Generic long-form export of all case metrics. |
| `report.md` | Human-readable campaign report. |
| `artifact_manifest.json` | Size and SHA-256 of every completed evidence file. |
| `cases/VPnn/` | Unmodified case-owned results and the captured `run.log`. |

The runner refuses a nonempty explicit output directory. This prevents a later
run from silently mixing products with earlier evidence.

## Case contract

An implemented case provides `vpNN/case.json` with this schema:

```json
{
  "schema_version": 1,
  "id": "VP01",
  "runner": [
    "{python}",
    "{case_dir}/run_vp01.py",
    "--output-dir",
    "{output_dir}"
  ],
  "result_file": "vp01_result.json",
  "download_argument": "--download",
  "no_plots_argument": "--no-plots"
}
```

The command is an argument array, not a shell string. Only `{python}`,
`{case_dir}`, and `{output_dir}` are expanded. This avoids quoting ambiguity and
shell injection while permitting relocation of the source tree. The optional
download and no-plot arguments are appended only when requested globally.

The declared result must be a JSON object with `schema_version`, matching
`validation_id` (or `id`), `status`, and an object-valued `metrics` member. A
runner that reports PASS must return zero, and a nonzero process may not claim
PASS. Every case should use exit `1` for a failed comparison and `2` for its own
setup/data failure; the global record preserves the process outcome and maps an
invalid pairing to ERROR.

## Adding a validation case

1. Create `test/validation/vpNN/` with a case README, immutable provenance,
   downloader when data are external, independent reference implementation,
   production API driver, focused tests, and case runner.
2. Make the runner accept `--output-dir`; add `--download` and `--no-plots` when
   applicable. It must write all generated evidence beneath that directory.
3. Write the case result last, after every comparison product is complete. Give
   each threshold, metric, provenance identifier, and limitation a stable name.
4. Add `case.json` using only the supported placeholders. Keep scientific
   parameters in the case runner, never in this launch contract.
5. Change the existing registry entry from `planned` to `implemented`. Do not
   reorder priorities or delete historical IDs. Dependencies must refer only to
   earlier cases, which keeps the campaign graph acyclic and reviewable.
6. Add a focused Make target if the case has a useful direct workflow, update
   this matrix and the case README, then run `make validation-test`, the case,
   `make validation-implemented`, and `make validation-campaign`.

Raw third-party archives should be ignored by Git and reproducibly downloaded
from identifiers and checksums in `data/PROVENANCE.json`. Small portable
reference outputs may be versioned when their license permits. Generated
executables, caches, logs, and transient campaign output must remain ignored.
