# Dedicated M2 builds and retained executable identity

The M2 Na/Ar builder is `build_m2_qualification.py`. It derives a uniquely
named temporary Config.pl application from the canonical Na-only compile
input, without editing that canonical input. The M2 purpose adds neutral Ar,
enables the declared radiogenic Ar source, compiles photochemistry OFF and
individual particle weights ON, and explicitly selects Mersenne Twister.
Those are the existing approved I19/I20 controls, not new physical laws.
Runtime sources, finite inventory, time/weight/seed settings and geometry
remain explicit in the `.in` receipt and are recorded by each linked run.

From an idle AMPS checkout, preferably a private verification copy:

```bash
python3 -B srcMoon/test/build_m2_qualification.py \
  --output-dir test_output/srcMoon/<new-campaign>/build \
  --spice-path /home/vtenishe/SPICE/cspice \
  --spice-kernels /home/vtenishe/SPICE/Kernels
```

Replace the documentation placeholder with a new campaign directory. The
builder removes only generated `build/`, uses the ordinary Config.pl path,
then runs bounded `make -j16` with explicit `-O3 -g`. It preserves its log,
commands, generated-mode checks, native source hashes and executable receipt.
Do not overlap its checkout-wide configuration transition with another build
or simulation. The global development runner supplies serialized ownership,
resource/deadline monitoring and the subsequent normal-build restoration.

The `--purpose sampling` variant is the earlier two-species sampling-storage
fixture; it retains canonical chemistry/RNG/weight choices and does not claim
the M2 chemistry or portable retained-build contract.

## Why the generated snapshots are required

A configuration-separated campaign builds M2, retains its executable, then
restores the normal Na-only application. The restored root `build/` belongs
to that later application. Comparing its headers against the earlier M2
binary would reject a valid retained executable for an unrelated build.
Conversely, compiling a local probe against those later headers and the old
M2 library can violate its generated ABI. The two uses require different
identity policies; source/executable hashes remain mandatory for both.

An M2 build therefore preserves exact generated bytes beside its executable:

```text
build/
  amps-moon-m2-na-ar
  build-m2-na-ar.json
  build-m2-na-ar.log
  generated-configuration/
    pic/picGlobal.dfn
    pic/pic.h
    general/rnd.h
```

The three files bind generated chemistry/particle controls, PIC configuration
and species/interface declarations, and RNG configuration. Every preserved
file is verified; recording a file without checking its bytes is insufficient.
Receipt paths are relative to the bundle, so copying the complete retained
directory does not require access to the original machine's build path.
Legacy absolute path records are readable only while their exact referenced
files remain available. Never reconstruct a missing snapshot from a newer
live build and call it preserved evidence.

## Two explicit verifier policies

```python
verify_retained_executable(executable)  # strict default
verify_retained_executable(executable, require_current_generated_tree=False)
```

The **strict default** is used by development/local-probe reuse. It verifies
the successful build receipt, exact executable, current authoritative native
source inputs, preserved snapshot hashes, and the matching current generated
tree. A later normal-profile restoration requires a new matching M2 build
before such probes can reuse the library/headers. Existing legacy live-only
receipts retain their historical live-tree checks, but they cannot claim the
self-contained retained ABI contract.

The **retained policy** is used by cluster/formal execution of the already
linked executable. It still verifies current native source and executable
identity and every preserved generated byte, and requires the complete
three-file snapshot set. It does not compare an unrelated root generated
tree or require that tree to exist. It never compiles a probe against a live
library. Missing snapshots remain an error even when live files happen to
match; a strict/current-tree fallback would defeat this policy.

Changing source, executable bytes, a snapshot, its recorded hash or the
chemistry/RNG contract invalidates reuse. New native sources are included in
the authoritative identity even before the user's eventual commit. A build
receipt PASS describes build/configuration identity only. It does not prove
numerical convergence, physical correctness, D02/D03 readiness, I13, or formal
I19/I20 qualification. All those scientific gates remain independently binding.

## Protocol tests

```bash
python3 -B srcMoon/test/test_m2_build_identity.py
```

The tests use temporary, explicitly labelled byte fixtures and never compile
or execute a physical model. They exercise real verifier file reads and
source collection: all preserved-header tampering, missing records/files,
wrong source/executable/status/contract hashes, added/removed native source,
bundle relocation, later live-profile changes, absent live builds, strict
default versus retained acceptance, and caller routing. The cluster fixture
retains SKIPPED for missing scientific evidence; the development fixture
deliberately stops before any native reuse. Neither fixture can become a
scientific PASS or observational evidence.
